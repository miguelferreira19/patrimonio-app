# V3.md — briefing de trabalho

Este ficheiro é o contexto MÍNIMO para trabalhar na V3. Existe para ninguém ter de ler o
`PLANO.md` (74 KB) para escrever um módulo de 200 linhas. O `PLANO.md` continua a ser a
história da V2 e o conhecimento de domínio de longo prazo; este é o que está a acontecer agora.

## O que a V3 muda

A V2 entregou três superfícies (Agora, Carteira, Ano) e um vocabulário visual. Falhou em quatro
pontos, e a V3 é a correção deles:

1. **É prosa, não é visual.** Frases inteiras como títulos, cinco elementos de texto por linha de
   decisão, um parágrafo a explicar cada gráfico.
2. **Estava construída para quem a usa todos os dias.** O viewer abre a app duas vezes por ano.
3. **Não olhava para a frente.** Todo o fluxo era histórico a 12 meses.
4. **A análise da renda era fina.** Há 12 anos de série mensal na base e usavam-se 12 meses.

Fases: F0 produção (feita) · F1 papéis (feita) · F2 Agora visual · F3 `renda.ts` ·
F4 `futuro.ts` · F5 conselhos · F6 `/analise` · F7 passagem visual ao resto.

## As cinco regras visuais (R1–R5)

Aplicam-se a **todo** o código novo e a todo o código que se toque.

| # | Regra | Em concreto |
|---|---|---|
| **R1** | **Um número herói por superfície, não uma frase.** | O topo de uma página é `Lede` com um número em Newsreader e no máximo 8 palavras à volta. Nunca uma frase inteira como título. `PageHeader` está `@deprecated` — não usar em código novo. |
| **R2** | **`Card` só quando há elevação real.** | Agrupar com `border-t border-regua` e uma etiqueta, ou com espaço em branco. `Card` fica para overlays e para o que está mesmo em cima do papel. Uma página que é uma pilha de `Card` é a assinatura de UI gerada. |
| **R3** | **O porquê não está sempre ligado.** | Numa linha de decisão fica visível: o quê, onde, quanto. O `porque`, a `conta` e a etiqueta de confiança colapsam para `<details>`. |
| **R4** | **Nenhum parágrafo explica um gráfico.** | Se o gráfico precisa de um parágrafo, o gráfico está mal desenhado. Os eixos e a legenda são a explicação. |
| **R5** | **Etiquetas maiúsculas com moderação.** | No máximo uma etiqueta `uppercase tracking` por cada três secções da página. |

## Sistema visual "papel e tinta"

Tudo em `src/app/globals.css` (Tailwind v4, `@theme`; **não existe `tailwind.config`**). O
cabeçalho desse ficheiro explica a estratégia inteira e vale a pena ler antes de mexer em cor.

- **Regra fundadora:** o que está confirmado é **tinta**; o que exige ação é **verde-cofre**; o
  que precisa de atenção é **âmbar**; o que é perda é **vermelho**; o que é desconhecido ou
  futuro é **ardósia**. **Não há verde de "ok"** — uma carteira sã é preta sobre papel. Verde de
  sucesso em código novo está errado.
- **Código novo usa só tokens semânticos**, que trocam de par com o tema sozinhos, **zero `dark:`**:
  `bg-papel bg-carta bg-elevado bg-vellum` · `text-tinta text-tinta-2 text-tinta-3` ·
  `border-regua border-regua-forte` · `text-acao bg-acao-tenue` · `atencao` · `perda` · `futuro`.
- As classes `zinc/teal/emerald/amber/red/sky` são **legado da V1**. Não escrever classes novas
  com elas.
- Fontes: Geist (UI), Geist Mono (meses, códigos matriciais, NIF), **Newsreader** (`font-serif`)
  só em ledes, títulos do Ano e a linha de dinheiro. Nunca serifa em chrome de UI.
- Separação por **hairline** (`border-regua`), nunca por sombra. Sombra só em overlay.
- Números: `tabular-nums` sempre. **Todo o euro passa pelo `<Money>`**; percentagens e áreas pelo
  `<Figure>`.
- Movimento: tokens `--t-*` e `--e-*`. Nada acima de 420 ms, nada em loop, entrada só no mount.
- **Proibido na UI:** travessões "—", emojis, gradientes néon ou roxos, animações infinitas.

## Componentes a reusar (não reimplementar)

- `src/components/kit/` — `Money`, `Figure`, `Lede`, `Confianca`, `Cobertura`. Sem hooks.
- `src/components/faixa/` — a faixa é a **única** implementação da grelha mensal.
- `src/components/ui.tsx` — `Card`, `Button`, `buttonClass`, `Input`, `Badge`, `Table/Th/Td`,
  `EmptyState`. **NUNCA acrescentar `"use client"` a este ficheiro**: as páginas server passam
  `icon={LucideIcon}` e a diretiva cria uma fronteira de serialização que as faz crashar em
  runtime sem o build falhar. Componentes com hooks vão para ficheiro próprio.
- `src/components/charts.tsx` — Recharts. Já é dependência; não trocar de biblioteca.

## Armadilhas do domínio (não redescobrir)

- **`receipts.amount` é ILÍQUIDO** (coluna "Valor" do Portal); o líquido é `amount - withholding`.
  Quem guarda cash líquido é `payments.amount`. Somar os dois foi o bug B1 e está no
  `irs.check.ts` como regressão.
- **`receipts.withholding` está a 0 em toda a base** — o reimport está pendente.
- **PostgREST devolve no máximo ~1000 linhas e `.limit()` não passa por cima disso.** Usar
  `paginateAll` (`src/lib/paginate.ts`) em `payments` e `receipts` (já há >5000 linhas).
- **`futuro` ≠ `falta`.** `src/lib/monthcell.ts` é a verdade única do estado de um mês
  (`pago|parcial|falta|fora|futuro`). Um mês além da fronteira de dados NUNCA é falta — era o
  bug B2.
- **A fronteira de dados** é `dataHorizonMonth(payments)`: o último mês com pagamentos. Nada para
  lá disso é conhecido.
- **O inquilino não é uma entidade.** É `contracts.tenant_name`, texto livre, com `tenant_nif`
  frequentemente nulo. Não há chave estável. Agrupar por NIF quando existe, senão por nome
  normalizado, e declarar a incerteza — nunca fuzzy match.
- **A tabela `expenses` está praticamente vazia**: nenhum import a povoa, todas as despesas são
  manuais. Qualquer número "líquido" que a app mostre é receita menos quase nada. Declarar, não
  estimar.
- **`area_m2` está por preencher em quase todas as fichas** → `marketView().estimatedValue` e
  `grossYield` são nulos na maioria da carteira. O ecrã de preenchimento em lote está em `/admin`.
- **Ano fiscal usa `issue_date`, não `ref_month`.** Um recibo multi-mês emitido em janeiro conta
  todo no ano de emissão. Para competência usa-se `ref_month`; para IRS, `issue_date`.
- **Ótica de FAMÍLIA**: valores por inteiro ("bolo"), sem repartir por quotas. As quotas de
  `property_owners` só entram no `irs.ts`.
- **Terrenos e vendidos ficam fora de toda a métrica corrente** (`isCurrentProperty`).

## Ambiente e gates

- Node **não** está no PATH. Em Git Bash, prefixar sempre:
  `export PATH="/c/Users/migue/AppData/Local/Logi/LogiPluginService/PluginHosts/node22/node:$PATH"`
- **Gate obrigatório:** `npm run build` **e** `npm run check`, os dois verdes, antes de dar
  qualquer tarefa por terminada.
- `npm run check` são self-checks **puros** com `node:assert`, compilados com `tsc` para `.check/`.
  Sem base de dados, sem framework de testes. **Nunca introduzir Jest ou Vitest.** Casos novos vão
  para o `*.check.ts` do módulo respetivo.
- Um módulo novo acrescenta o seu `check:<mod>` ao script `check` do `package.json`.
- Escrita na base só por server action com `requireAdmin` (`src/lib/actions/*`).
- **Sem dependências novas.** Já existem: lucide-react, recharts, clsx, tailwind-merge, papaparse,
  xlsx.
- `dados/` tem dados pessoais reais e está no `.gitignore` — nunca commitar nem expor.
- Sem commits nem push sem pedido explícito.

## Contrato de um módulo puro da V3

Quem recebe uma tarefa de módulo (`renda.ts`, `futuro.ts`, geradores) entrega:

1. o módulo em `src/lib/portfolio/`, **sem I/O, sem React, sem `new Date()` escondido** — o
   relógio entra sempre por parâmetro, que é o que permite testar com relógio fixo;
2. o `*.check.ts` ao lado, com os casos-limite nomeados;
3. a entrada `check:<mod>` no `package.json`, acrescentada ao script `check`;
4. `npm run build` e `npm run check` verdes.

Proibido: tocar em UI, acrescentar dependências, mexer no schema, reimplementar o que a tabela
acima já dá.
